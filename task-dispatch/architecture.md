# 架构与技术设计说明

## 1. 选型：为什么是这个组合

**Node.js + TypeScript + Express + node:sqlite（单代码库、两个入口：Coordinator / Worker）。**

| 决策点 | 选择 | 理由 |
|---|---|---|
| 语言/运行时 | Node.js + TypeScript | 团队熟悉（与既有项目一致）；单进程异步模型天然适合 Worker 的节点内并发 |
| Web 框架 | Express | 足够简单，业务方接口与内部接口都只是普通 HTTP |
| 状态存储 | SQLite（`node:sqlite` 内置模块） | 零部署成本；**同步 API 是关键**——Coordinator 内所有状态变更是串行处理的，这让"原子领取"可以用单条 SQL 表达而不需要分布式锁 |
| 队列中间件 | 不用（自实现） | 题目要求调度核心逻辑自己实现，不依赖已完整实现该功能的云服务或框架；SQLite 的 tasks 表 + 状态机就是队列 |
| 分发模型 | **拉模型**（Worker 轮询领取） | 见第 3 节权衡表 |
| 执行 | mock（接口抽象可切真实 python3） | 题目明确考查重点在调度协调，不在真实执行 |

## 2. 关键模块工作原理

### 2.1 原子领取——为什么一条 UPDATE 就够了

领取 = 「从队列取一个任务」+「标记为我的」。若拆成两步（SELECT 再 UPDATE），两个节点就会在中间窗口抢到同一个任务。本设计把它们合成一条：

```sql
UPDATE tasks SET status='running', worker_id=:w, ...
WHERE id = (SELECT id FROM tasks WHERE status='queued' ORDER BY created_at, id LIMIT 1)
RETURNING *;
```

正确性来自两层保证：**进程内** node:sqlite 同步 API 使请求串行执行，根本不存在并发写交错；**进程间**（未来 Coordinator 多实例时）SQLite 写事务互斥锁让两条该语句严格先后提交，后者 WHERE 不再命中。`RETURNING` 让"谁领到了"这件事与状态变更在同一条语句内完成，没有窗口期。

### 2.2 心跳 + 超时回收——租约（Lease）思想

Worker 领取任务的同时获得一份**租约**：持续心跳则续约，心跳停止则租约过期。Coordinator 的回收器把"过期租约"的任务放回队列。这解决了分布式系统里最头疼的"节点失联"问题：

- 不需要"节点故障检测"这种精确而昂贵的东西——超时即失联，宁错杀（被误回收的任务重试一次而已）不遗漏；
- 任务不会永久卡在 running（租约上限 = 心跳间隔 + 租约超时，默认 10s）；
- 迟到的旧租约回写被状态机前置条件拒绝，天然解决"双主"式冲突。

### 2.3 幂等的根基——状态机前置条件

所有状态迁移接口都要求"当前状态符合前置条件才执行"（claim 要求 queued、complete 要求 running 且归属一致）。**迁移与校验在同一条原子 SQL 里**。这带来两个性质：任务最多执行一次；结果最多写一次。第 7、8 节的设计文档给出完整故障推演与证明。

### 2.4 节点内并发、节点间零共享

- **节点内部**：每个 Worker 是一个进程，内部用异步并发池（默认 3）同时跑多个任务——题目允许的单机手段全部可用；
- **节点之间**：只存在三条 HTTP 通道（claim / complete / heartbeat），无共享内存、无全局变量、无文件共享——把 Worker 挪到另一台机器，改一行 `COORDINATOR_URL` 即可，代码零改动。这是"按真实分布式设计"的硬约束，也是本架构的验收点。

### 2.5 状态持久化与重启恢复

任务全部状态持久化在 Coordinator 的 SQLite 中；Worker 完全无状态。任何组件重启后都能从持久化状态自愈（Coordinator 启动扫描 running 残留、Worker 启动即注册轮询），见设计文档 6.4。

## 3. 设计权衡

| 权衡 | 选择的方案 | 代价 | 为什么可接受 |
|---|---|---|---|
| 拉模型 vs 推模型 | Worker 轮询（默认每 200ms 领取） | 空队列时存在轮询开销；领取有毫秒级延迟 | 节点自恢复能力强（重启即归队）；天然限流（节点按能力领取）；无需注册中心与健康检查；5 节点规模轮询开销可忽略 |
| SQLite vs Redis/消息队列 | SQLite | Coordinator 单点、并发写吞吐有限 | 内部工具量级（5 节点 × 3 并发）远低于 SQLite 能力；换来零部署、单语句原子性；演进路径见下 |
| 同步 SQLite 驱动 vs 异步 | 同步 | 单个慢查询会阻塞事件循环 | 本系统查询均为毫秒级索引查询；同步驱动换来了"无需显式加锁"的正确性 |
| 轮询间隔 vs 领取延迟 | 200ms | 排队任务平均多等 ~100ms | 任务执行时长秒级，毫秒级分发延迟无感知；可调 |
| 超时误回收 | 10s 租约 | 假死节点（长 GC/暂停）任务被重执行——但恰好一次保证的是"结果唯一"，重试由状态机幂等兜底 | 重试有上限、结果只写一次，业务方看到的是正确终态 |

## 4. 与"真实分布式"要求的一致性检查

题目要求：节点之间不能依赖共享内存/全局变量，只能通过网络通信协调。

| 检查项 | 结论 |
|---|---|
| 节点间通信方式 | 仅 HTTP 内部接口（claim/complete/heartbeat），无任何内存/文件共享 ✅ |
| 节点故障不影响他节点 | Worker 独立进程独立生命周期；kill 任意节点，其余照常，任务由租约回收转交 ✅ |
| 协调逻辑不依赖单机假设 | 领取/回收/幂等全部由持久化状态机表达，Coordinator 地址是 Worker 唯一的环境依赖 ✅ |
| 单机手段只用在节点内部 | 并发池、异步等待仅存在于 Worker 进程内 ✅ |

## 5. 演进路径

1. **状态后端替换**：tasks 表搬到 Redis/PostgreSQL；原子领取换 `BLMOVE` 或 `SELECT ... FOR UPDATE SKIP LOCKED`——调度协议（claim/complete/heartbeat 语义）不变；
2. **Coordinator 高可用**：主备 + 选主（租约锁）；回收器跟随主切换；
3. **Worker 动态扩缩容**：注册制 + 优雅下线（不再领取、跑完在途任务、注销）；
4. **推送模式**：若延迟要求变高，在"领取"协议上加长连接推送（SSE/WebSocket），仍是同一状态机；
5. **结果对象化**：大结果存对象存储，任务行只存引用；
6. **安全**：内部接口 token/mTLS；业务方接口限流与配额。
