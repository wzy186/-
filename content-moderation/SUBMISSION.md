# SUBMISSION.md — 解题过程与 AI 协作说明

## 1. 项目是什么

内部运营审核用户投稿的值班工具。核心场景：**看列表 → 勾选几条 → 通过或驳回**，一次处理多条，情况未必相同。

技术栈：Vue 3 + TypeScript（前端）、Node.js + TypeScript + Express（后端）、本地 SQLite（Node 内置 `node:sqlite`，零原生编译依赖）。运行方式见 [README.md](./README.md)。

## 2. 题面没写清、我自己的假设

| 项 | 我的决定 | 理由 |
|---|---|---|
| 投稿形态 | 标题 + 正文 + 可选图片（1~4 张 URL） | 「文本+图片」覆盖面最典型；演示数据用可访问的占位图（picsum.photos），列表能看缩略图 |
| 审核结论 | 只有 通过 / 驳回 两种，驳回必须填原因 | 题面只要求这两种；加原因是为了驳回可追溯 |
| 驳回原因 | 6 个预设（广告营销/内容低俗/人身攻击/敏感违规/灌水无意义/其他）+ 可追加自定义说明 | 值班效率优先，预设一键选；「其他」时必填自定义文本 |
| 状态机 | 待审核 → 已通过 / 已驳回；已审条目可「重新审核」打回待审核，打回时清空原审核信息 | 误审打回是值班场景的刚需 |
| 「谁在操作」 | 不做账号体系：右上角下拉选「当前操作人」（值班同事名单预置），选择存 localStorage，随每次操作写入日志 | 题目明确说「用你觉得够用的方式即可，在说明里写一句」——就是这句 |
| 批量审核 | 勾选跨页保留；批量操作只处理仍处于待审核的条目，其余跳过并提示数量 | 多人同时值班时可能撞单，静默覆盖别人刚审完的结果是错的 |
| 演示数据 | 48 条：30 条待审核 + 18 条已审历史（跨过去 7 天，含少量「重新审核」记录），内容刻意混入广告/低俗/辱骂/谣言/灌水题材 | 让演示时真的有东西可审、可驳回；已审历史让统计看板第一天打开就有内容 |
| 统计口径 | 「今日」按本地自然日；通过率 = 通过 ÷ (通过+驳回)；重新审核不计入处理量 | 值班交接关心的是今天处理了多少、放行比例 |
| 端口 | 后端 3000，前端 dev 5173（代理 /api）；生产模式后端直接托管前端产物 | 一条 `npm run dev` 起全部，`npm run build && npm start` 单端口交付 |
| 技术选型细节 | SQLite 用 Node 内置 `node:sqlite` 而非 better-sqlite3 | 避免原生模块编译失败（评审机器环境不可控），Node ≥ 22.13 即可 |

## 3. 实现过程（按时间顺序）

1. **需求澄清**：先和 AI 对齐了四个决定点——代码放 `wzy186/-` 的子目录（仓库里已有 TravelMate 等项目，不动它们）、投稿形态、功能范围（选完整版：核心 + 日志 + 统计看板）、代码推送方式（AI 完成后我自己推）。
2. **项目骨架**：npm workspaces 单仓库（`server/` + `web/`），根目录一条 `npm install`、一条 `npm run dev`。
3. **后端先行**：表结构（`operators` / `submissions` / `review_logs`）→ 演示数据生成（固定随机种子，每次重置结果一致）→ 全部 API（列表筛选搜索分页、单条/批量审核、日志、统计）→ curl 冒烟测试。
4. **前端**：Vite + Vue 3 + Element Plus 脚手架 → 审核队列页（核心）→ 操作日志页 → 统计看板页（手写 CSS 柱状图/堆叠条，不引图表库，KPI 用数字卡片）。
5. **端到端验证**：类型检查、前后端构建、生产模式静态托管、完整审核流程走查（详见第 5 节）。

## 4. 与 AI 的协作方式

**工具**：全程使用 Claude Code（CLI）完成，未手工编写大段代码；代码、文档、演示数据由 AI 生成，我负责定需求、做决定、审查结果。

**协作模式是「提问 → 实现 → 验证」的循环，我的角色是决策者和验收人：**

- **需求澄清阶段**：我先把题目喂给 AI，AI 没有直接开写，而是先问了我 4 个题面没写清的问题（代码放哪个仓库/子目录、投稿形态、功能范围、推送方式），我逐条拍板。这些决定最后都落进了第 2 节的假设表。
- **实现阶段**：AI 按我确认的方案从零生成前后端代码。我要求它先做后端并用 curl 验证接口，再做前端——这样前端联调时数据层已经是可靠的。
- **验收阶段（关键）**：AI 自己发现问题、我复核确认，至少三轮：
  1. node:sqlite 类型严格，AI 生成的类型转换代码过不了 `tsc`，它按报错逐处修正（参数类型收窄、`unknown` 转换）——我确认它没有靠 `any` 糊弄过去，最终 `strict: true` 全过。
  2. curl 冒烟测试发现**真 bug**：SQL `SELECT *` 返回 snake_case 列名，但序列化层按 camelCase 读，导致图片列表、审核人、审核时间在 API 响应里全部丢失；另有一个统计边界 bug（用 JS 最大 Date 的 ISO 串做字典序比较失效，导致「累计处理量」恒为 0）。都由 AI 定位修复后我复测确认。
  3. 演示数据第一版散得太开（近 7 日有几天为 0），我看了统计接口输出后要求把历史数据均匀铺满 7 天，让看板第一天打开就有完整图形。
- **我自己做的事**：拍板所有需求决策；审查接口行为（如批量审核跳过非待审核条目、重新审核清空原审核信息这些语义，是我验收时要求明确的行为）；检查演示数据的真实性（每条中文投稿内容我过了一遍）；最后跑通完整流程。
- **图表部分**：AI 按 dataviz 规范做了配色校验（Element Plus 状态色通过色盲可分辨性检查，对比度不足用「柱上直接标数值 + 图例 + 明细表」弥补），统计看板没有引入额外图表库，全部手写 CSS。

## 5. 验证情况

- 后端 `tsc --noEmit`（strict）通过；前端 `vue-tsc --noEmit` + `vite build` 通过。
- 接口流程 curl 全走查：列表筛选/搜索/分页 → 单条通过 → 重复审核被 409 拒绝 → 重新审核 → 驳回（缺原因被 400 拒绝）→ 批量驳回 → 日志记录 → 统计数字同步变化。
- 生产模式：`npm run build && npm start` 后单端口 3000 同时提供页面与 API，SPA 深链接（/logs）回退正常。
- 开发模式：vite 5173 代理 /api 正常。
- **提交前做了一轮多角度代码审查**（AI 以 10 个不同视角并行扫同一份 diff，再逐条去重验证），其中 4 个服务端 bug 先用 curl 实证复现再修复，修复后回归复测全部通过。摘要有代表性的几类：
  - 搜索词中的 `%`/`_` 会被当成 LIKE 通配符（搜 `%` 返回全表）→ 转义 + ESCAPE 子句，回归验证 `q=%` 只命中 1 条真实含 `%` 的投稿；
  - 分页参数传小数（`pageSize=2.5`）会让 SQLite 抛错返回 500 → 非正整数一律回退默认值；
  - 请求体 JSON 格式错误被统一报成 500 → 按错误类型如实返回 400/413；
  - 凌晨（00:00~05:00）首次灌演示数据时，「今天已处理」的记录会落到昨天 → 改为按本地自然日零点计算时间窗口；
  - 前端列表加载存在竞态（旧响应可能覆盖新结果）、通过按钮双击可重复提交、他人已处理的条目 409 后列表不刷新 → 请求序号守卫、动作互斥、失败也刷新；
  - 前后端各存一份驳回原因预设，靠注释约定「保持一致」→ 改由后端 `/api/meta` 下发，前端只留「其他（自定义）」入口。
- **自动化测试**：`npm test`（Node 内置 node:test + 断言，零新增依赖），7 组 API 集成测试跑在独立临时数据库上、不污染演示数据，覆盖：种子数据与统计口径（48 条、今日与近 7 日均有数据、时间戳合法）、分页与非法参数回退、LIKE 字面量转义（`%`/`_` 不当通配符）、审核状态机全生命周期（通过 → 重复 409 → 重新审核 → 驳回校验 → 已驳回再操作 409）、批量审核跳过计数与上限、日志筛选、坏 JSON 与未知接口的错误状态码。为可测试性把 Express 应用拆成 `app.ts`（`createApp()`）与 `index.ts`（启动入口），数据库路径支持环境变量注入临时库。全部 7 组通过。
- 浏览器端的视觉细节请以运行效果为准（本环境无浏览器，未做截图级验收）。

## 2026-10-12 13:23 后端联调踩了两个坑

开发按"后端先行、curl 验证"的节奏走，第一轮联调就查出两个真 bug：

1. **接口返回的审核字段全丢了**：SQL `SELECT *` 出来的列名是 snake_case（`image_urls` 这种），但序列化的时候按 camelCase 读，图片、审核人、审核时间全没了。改法是在查询里显式写别名（`image_urls AS imageUrls`），别指望两边默认对齐。
2. **累计处理量一直是 0**：统计全量区间的上界用了 JS 最大日期转出来的 ISO 字符串，那个串带 `+` 号，按字典序比的时候反而比正常日期小。改成写死 `9999-12-31T23:59:59.999Z` 就好了。

另外第一版演示数据被我打回去了：历史记录散到了 13 天外，近 7 日里有几天是空的。我让它把 48 条重新铺满近 7 天，不然看板第一天打开就缺柱子，太假。

## 2026-10-12 13:56 翻页没反应的 bug

前端写完之后 AI 自查出来的：两个列表页的分页器改了 page 之后没有 watch 触发重新加载，等于翻页点了没反应。这种"状态改了、反应链没接上"的问题很隐蔽，类型检查、构建都发现不了。改法是让分页状态统一走 watcher 触发 `load()`，顺便把"当前页审空后回退"的逻辑从 `load()` 里的递归挪出来，交给 watcher 处理，避免重复请求。

## 2026-10-13 12:15 验收修复：驳回弹窗原因勾选不了

验收时发现一个交互 bug：点「驳回」打开弹窗后，6 个驳回原因怎么点都勾选不上，单选圈始终不亮。

**问题在哪**：浏览器控制台刷了一排 Vue 警告——`Invalid prop: type check failed for prop "value". Expected String | Number | Boolean, got Object`。根源是我第一版的设计：让 `el-radio` 的 value 直接绑定一个对象 `{ label, custom }`，想用它同时携带「原因文案」和「是否自定义」两个信息。但 Element Plus 的 radio 值类型只支持字符串/数字/布尔，内部用 `===` 判断选中态——对象每次渲染都是新引用，`===` 永远不成立，所以点谁都选不中。这是我选型时没查清组件 API 类型约束导致的，属于过度设计。

**为什么之前没发现**：此前的验证集中在接口层（curl 走查 + 集成测试 + 类型检查），浏览器交互没有逐按钮点到这个弹窗。这次验收我用 headless Chrome 驱动真实页面复现，从组件实例里读出 radio 值与模型值的引用关系，确认是引用不等导致选中态失效，和那排类型警告完全对上。

**怎么修的**：我决定把 radio 值改成原因文案字符串本身（value 直接用「广告营销」等文案），「自定义原因」不再靠对象字段标记，改为「是否选中『其他』」判断。这个方案最贴合组件库的类型约束，改动也最小：删掉 RejectOption 接口和 rejectOptions 计算属性，composeReason 相应调整，模板里预设原因直接遍历 rejectReasons、末尾追加固定的「其他」项。AI 按这个方案实现后我复测：默认选中第一个原因、点击可正常切换、选「其他」时补充说明输入框切换为必填提示；端到端驳回一条投稿成功，日志正确留痕（原因、操作人、时间齐全），控制台警告清零。后端 7 组集成测试、前端 vue-tsc 类型检查全过。

**反思**：组件库 value 的类型约束属于「选型时就要查清楚」的边界，第一版用对象携带双信息是过度设计；验收必须覆盖浏览器交互路径，纯接口级验证会漏掉这类 UI 层 bug。修复已提交（commit `dcacc08`）。
