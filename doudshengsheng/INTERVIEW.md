## 三、核心技术点深挖

### 3.1 缓存三大问题(商铺查询)

**接口**:`GET /shop/{id}?strategy=pass-through|mutex|logical`

我把三种解法都实现了,可通过参数切换,面试时讲"我对比了三种方案"。

#### 缓存穿透(查不存在的数据)
- **方案**:布隆过滤器 + 空值缓存**组合**(双层防线)。
  - **第一层 布隆过滤器**:Redisson `RBloomFilter`,启动时预热所有商铺 id(容量 10 万 / 误判率 1% / 约 100KB)。查询前先 `contains(id)`,说"不存在"直接返回,**不查缓存不查 DB**——挡掉 99% 恶意穿透,且是确定性判断不依赖 TTL。
  - **第二层 空值缓存**:兜底布隆的误判(那 1% 说"存在"但实际不存在的)。查 DB 为 null 时缓存空字符串 `""`,短 TTL(2 分钟)。
- **为什么组合用?** 布隆说"不存在"一定不存在(确定性),但说"存在"可能误判。空值缓存恰好兜底误判——两者互补,单独用任一个都有缺口。
- **追问:布隆的坑?**
  - **不支持删除**:标准布隆删了商铺不能从过滤器移除。删商铺后该 id 仍"存在"于布隆,查询会过布隆但 DB 查空 → 走空值缓存兜底。要支持删除得换**布谷鸟过滤器**(Redisson `RCuckooFilter`)。
  - **新增必须同步 add**:新增商铺时必须 `bloomFilter.add(id)`,否则新商铺被布隆挡住查不到。我的 `save()` 接口做了这个。
  - **容量预估**:`tryInit(容量, 误判率)`,超容量后误判率上升,要按业务峰值预估。
- **代码**:`BloomFilterConfig`(预热)、`ShopServiceImpl.queryById`(前置判断)、`ShopServiceImpl.save`(新增同步 add)。
- **验证**:查不存在的 id 9999,日志无 SQL(布隆在前面拦了,没查 DB);查存在的正常返回;新增后能查到。

#### 缓存击穿(热点 key 过期瞬间,大量请求打到 DB)
- **方案 A:互斥锁**。缓存未命中时,`SETNX` 抢锁,只放一个线程查 DB 重建,其他线程休眠重试。双重检查防重复重建。
- **方案 B:逻辑过期**。不设 Redis TTL,值里带 `expireTime` 字段。读到过期时,开异步线程重建(抢锁),当前线程返回旧数据。
- **追问:两种怎么选?**
  > 互斥锁强一致,吞吐降;逻辑过期高吞吐,短时不一致。秒杀这种要强的选互斥锁,商铺查询这种容忍短暂不一致的选逻辑过期。逻辑过期需要预热(不能冷启动)。

#### 缓存雪崩(大量 key 同时过期)
- **方案**:TTL 加随机数。`CACHE_SHOP_TTL + random(10)` 分钟,打散过期时间。

#### 写策略(更新商铺)
- **先更新 DB,再删缓存**。不能先删缓存后更 DB(并发下会有脏读)。删而非更新,避免并发写冲突。

### 3.2 优惠券秒杀(面试高频)

**接口**:`POST /voucher/order/seckill/{id}`

**完整链路**:
```
请求 → Lua 脚本(原子:时间校验+库存+一人一单+扣减) → 发 Stream → 返回
                                                        ↓
                                              异步消费者:分布式锁兜底 + 落库 + ACK
```

#### 全局唯一 ID
- **结构**:符号位(1) + 时间戳(31 位,从 2024-01-01 起算秒) + 序列号(32 位,Redis INCR)。
- **为什么不用 DB 自增?** 分库分表后会冲突;自增暴露业务量;ID 不连续容易被猜测。
- **为什么时间戳在高位?** 趋势递增,落入 B+ 树索引有序,写性能好。
- **测试**:并发 100 线程 × 100 次 = 10000 个 ID 全唯一(有单测验证)。

#### Lua 原子扣库存
- **脚本** `seckill.lua`:时间判断 → `SISMEMBER` 查一人一单 → `GET` 库存 → `DECR` 扣减 → `SADD` 记录用户,四步原子。
- **为什么用 Lua?** Redis 单线程执行 Lua,天然原子。否则"判断+扣减"两步之间会有并发窗口,导致超卖或重复下单。
- **追问:为什么不直接用 DB 事务?** DB 事务行锁性能差,扛不住秒杀几千 QPS。Redis 几十万 QPS,把核心判断放 Redis,MySQL 只异步落库。

#### Redisson 分布式锁(异步消费者兜底)
- 消费者拿到消息后,`redisson.getLock("lock:order:" + userId).tryLock()`,锁内落库。
- **追问:Lua 已经挡了一人一单,为什么还要分布式锁?** 双保险。Lua 在 Redis 层挡 99%,万一有边界情况(如 Lua 执行异常后 Stream 重投),DB 唯一键 + 分布式锁兜底。体现"防御性编程"。
- **追问:Redisson 看门狗原理?** 拿锁后开个后台线程,每隔 1/3 TTL 续期,防止业务执行久锁过期。默认 30s TTL。

#### Stream 异步落库
- 秒杀成功后 `XADD` 发消息,消费者 `XREADGROUP` 消费,落库后 `XACK`。
- **追问:为什么不用阻塞队列?** 阻塞队列是 JVM 内存,服务重启丢数据。Stream 持久化在 Redis,宕机不丢,且有消费组支持多消费者。
- **追问:消息丢了怎么办?** 消费者没 ACK 的消息进 PEL(待处理队列),可用 `XPENDING` + `XCLAIM` 重新分配给其他消费者。

### 3.3 红包雨(面试杀手锏,重点讲)

**这是我自己设计的,教程里没有现成答案,体现独立思考。**

#### 二倍均值法拆金额
- **公式**:每次拆的金额 ∈ `[1, 剩余金额/剩余人数 × 2 - 1]`,最后一人拿剩余。
- **性质**(我写了单测验证):
  1. 每人至少 1 分
  2. 总额守恒:拆分之和 == 输入总额
  3. 任意抢的顺序下,期望公平
- **为什么不用普通随机?** 普通随机会让先抢的人期望偏高、后抢的吃亏。二倍均值法保证期望相等。
- **举例**:100 元 10 人。第一人区间 `[0.01, 100/10×2-0.01]=[0.01, 19.99]`,假设抢 15,剩 85 元 9 人,第二人区间 `[0.01, 85/9×2-0.01]=[0.01, 18.88]`...
- **实现**:`RedPacketSplitter` 工具类,我特意提取成独立类——为了可测试性,算法独立可复用。有 27 个单测 case(含 20 次随机参数验证不变量)。

#### 预分配金额到 List
- 创建红包时一次拆好所有金额,`RPUSH` 到 `redpacket:{id}:amounts`。
- 抢的时候 `RPOP` 是 O(1),Lua 临界区极短。
- **为什么不抢时再算?** 在 Lua 里做随机+更新,逻辑重、锁竞争久。预分配把重活前置,抢的路径极简。

#### Lua 原子抢红包(`redpacket_grab.lua`)
- 幂等(`HEXISTS` 查已领)→ `RPOP` 取金额 → `HSET` 记录 → `HINCRBY remain -1`,四步原子。
- 返回值:`金额`(成功)/ `-1`(已领)/ `0`(抢完)。

#### 滑动窗口限流防刷(`sliding_window.lua`)
- ZSet 存请求时间戳,`ZREMRANGEBYSCORE` 清窗口外,`ZCARD` 统计,超阈值拒绝。
- **追问:为什么不用固定窗口?** 固定窗口有临界点突变(窗口边界附近双倍流量)。滑动窗口平滑。
- 配置:10 秒内最多抢 3 次,超出 429。

#### Stream 异步落库(批量)
- 抢到金额后发 Stream,消费者批量(50 条)落库 + 批量 ACK。
- **追问:为什么批量?** 减少 DB 交互次数,提升吞吐。单条 insert QPS 几千,批量能上万。

#### 延迟队列未领退款
- 创建时 `ScheduledExecutor.schedule(refund, refundDelaySeconds)`,到期扫描未领金额,标记红包状态为"已退款关闭"。
- **追问:服务重启了延迟任务怎么办?** 这是当前实现的局限(`ScheduledExecutor` 是 JVM 内存,重启丢)。生产方案:Redisson `DelayedQueue` 或 Redis ZSet 做延迟队列(时间戳做 score,定时扫描)。面试时主动说"这是可优化点",体现认知。

### 3.4 其他 Redis 应用

| 场景 | 实现 | 关键点 |
|------|------|--------|
| 点赞排行榜 | ZSet(uid, 时间戳) | 一人一赞(score 唯一),按时间排序取 Top5 |
| 共同关注 | Set 交集 | `SINTER follow:{a} follow:{b}` |
| Feed 流(推模式) | ZSet(blogId, 时间戳) | 发笔记时遍历粉丝推送到各自收件箱,滚动分页 |
| 附近商铺 | GEO + GeoSearch | `GEOSEARCH key FROMLONLAT x y BYRADIUS` |

**Feed 流推模式 vs 拉模式**(常问):
- 推模式:发笔记时主动推给粉丝(写放大,读快)。适合粉丝少的场景。
- 拉模式:粉丝主动拉关注人的最新(读放大,写快)。适合大 V 粉丝多的场景。
- 我选推模式:普通用户粉丝不多,读体验优先。

## 四、踩的坑(面试加分项,体现实战)

### 4.1 Long 精度丢失(前后端协作经典坑)
- **现象**:前端抢红包显示"红包已抢完",但红包明明有库存。
- **排查**:对比后端返回的场次 ID `353850840710119816` 和前端拿到的 `353850840710119800`——末尾精度丢了。
- **根因**:雪花 ID 超过 JS `Number.MAX_SAFE_INTEGER`(2^53 ≈ 9×10^15),`JSON.parse` 把 Long 当 Number 丢精度。
- **修复**:`JacksonConfig` 把 Long 序列化成 String 传前端。

### 4.2 JacksonConfig 覆盖 JavaTimeModule(这个坑更隐蔽)
- **现象**:加了 JacksonConfig 后,商铺接口全 500,报 `LocalDateTime not supported`。
- **根因**:我用 `builder.modules(longModule)` 注册自定义模块,`modules()` 是**覆盖语义**,把 SpringBoot 默认注册的 `JavaTimeModule` 冲掉了。
- **修复**:改用 `builder.modulesToInstall(longModule, new JavaTimeModule())`,追加而非覆盖。
- **讲法**:这是 SpringBoot 自定义 Jackson 的经典坑,`modules()` vs `modulesToInstall()` 语义不同。

### 4.3 自调用事务失效
- **现象**:Stream 消费者里调 `this.handleRecord()` 标了 `@Transactional`,但事务不生效。
- **根因**:Spring AOP 基于代理,`this` 内部调用不走代理。
- **修复**:改用 `TransactionTemplate` 显式管理事务(消费线程本就不在 Tomcat,用编程式事务更合适)。

### 4.4 Stream 消费死循环拖垮服务(压测发现的真 bug)
- **现象**:压测时后端 8081 突然不响应,日志疯狂刷 `Redisson is shutdown`,进程卡死。
- **根因**:Stream 消费者 `while(!isInterrupted)` 循环里 `catch(Exception)` 只打日志不退避。Redis 连接被打满触发 Redisson shutdown 后,消费线程陷入死循环,1 秒内打几万行日志,把 Tomcat 线程和磁盘 IO 拖垮。
- **修复**:catch 后 `Thread.sleep(1000)` 退避,且捕获 `InterruptedException` 时退出循环。
- **讲法**:这是"异常处理只 catch 不 recover"的反面教材。任何 while 循环里的 catch 必须有退避或退出策略,否则一个底层故障会放大成服务雪崩。压测才暴露这种问题,单元测试测不出来。

## 六、高频追问预案

**Q: 这项目能上线吗?**
> 能跑,但离生产还有距离:① 没做管理员权限校验(后台裸奔);② 延迟队列用 JVM 内存,重启丢;③ 没做监控告警;④ 前后端应分离部署上 CDN。这些我都知道,是刻意没做(演示项目范围)。

**Q: QPS 能到多少?**
> 压测过(本机,12 核,Redis/MySQL/后端同机,非纯净环境):
> - **商铺缓存读**:ab 压测,并发 100 时 **~8000 QPS / 12ms**,并发 200 峰值 ~8000 QPS,500 并发后延迟上升到 75ms(拐点)。0 失败。瓶颈在 Tomcat 线程 + Redis 连接,不在 DB(缓存命中不碰 DB)。
> - **秒杀并发**:500 用户抢 200 库存,**成功 200、失败 300(全"库存不足")、0 超卖**,DB 落库 200 单一致。验证 Lua 原子扣减在并发下无超卖。
> - **红包雨并发**:300 用户抢 50 个红包(100 元),**抢到 50 人、金额守恒(10000 分 == 100 元)、0 超领**。验证二倍均值法总额守恒 + Lua 原子抢。
>
> 说明:秒杀/红包的 QPS 数字受 bash + curl 启动开销限制偏低(~60),不代表后端真实吞吐;真实吞吐看商铺缓存读的 ab 数据(8000 QPS)。秒杀压测的重点是**并发正确性(无超卖/金额守恒)**,不是吞吐,这个目标已达成。
> 生产环境 Redis 单实例理论 10 万 QPS,秒杀核心路径只碰 Redis(Lua + Stream),MySQL 异步落库削峰,瓶颈在 Redis 不在 DB。

**Q: 如果 Redis 挂了怎么办?**
> 当前没做 Redis 集群/哨兵。生产应 Redis Cluster + 本地缓存(Caffeine)兜底。秒杀场景 Redis 挂了应降级(直接拒绝或排队),不能让请求打到 DB。

**Q: 数据一致性怎么保证?**
> 秒杀:Redis 扣减和 DB 落库最终一致(Stream + ACK + PEL 重试)。商铺缓存:先更 DB 再删缓存,有短暂不一致窗口,可加延迟双删。

**Q: 为什么选 Redis 不选别的?**
> 秒杀/红包这种高并发读多写少、且需要原子操作的场景,Redis 单线程 + 丰富数据结构 + Lua 天然合适。MySQL 扛不住,Memcached 没有数据结构和持久化。
